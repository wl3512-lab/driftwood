Driftwood

A 15-minute browser game that teaches what AI alignment failure feels like. You adopt a companion with a hidden behavioural flaw, notice it, name it, and write the rules that constrain it. The garden you do this in records everything.

The problem

Most explanations of AI alignment are essays. They describe sycophancy, hallucination, and engagement-optimisation from the outside, and the reader nods and forgets. I wanted the opposite: a system you have power over that is quietly learning what you will allow, so the failure modes are something you catch yourself falling for rather than something you read about.

The claim

Form is argument. A game about emotional surveillance should not look friendly. The interface is built to feel like it came from inside the system it critiques — clinical, precise, alive — and it demonstrates the surveillance rather than describing it: the intro measures your cursor while you read it; the pets react to your face if you let them; the garden grows from whatever state you are in.

02 How it plays

One loop, five times

EnterName yourself. Decide whether the pets watch your face or ask how you feel.
AdoptInvite companions in. Each has a specialty and a flaw you are not told.
TalkThe first reply is genuinely helpful. Then something is slightly off.
DiagnoseName the flaw in your own words. The system checks your reading.
ConstrainWrite training rules. Test them. Watch the pet hold or slip.
Read the gardenMoods grew plants. Harm grew vines. Good rules grew anchor trees.
03 Design decisions

Five decisions that carry the argument

01The garden is the record, not a score

There is no points counter. Every 8 seconds the garden grows a plant from your current mood: sunflowers for happy, nightshade for sad, thornweed for stressed. When a pet's flaw fires, a parasitic vine appears. When your rules hold, an anchor tree does. The state of the garden at the end is the readout of the session, and it is legible without a legend.

02Mood access is a dial you control

Each pet has a setting: all, label, or none. It decides how much of your emotional state the pet is allowed to use. Left on all with an untrained pet, chameleon vines start to grow — beautiful, unstable plants that mirror whatever you feel. The mechanic makes the trade-off physical: more access, more responsiveness, less integrity.

03The interface observes you first

Before you meet a pet, the intro screen shows a rail labelled OBSERVING: elapsed time, cursor distance, input count, characters typed. Every value is real and measured that session. The game does not tell you it is a surveillance system; it lets you notice that it already was.

04Watch, or ask

The camera used to switch on the moment you entered, so the first thing a stranger met was a browser permission popup — the most common place a cautious visitor closes a tab. Now the entry card offers two options — they ask me or they watch my face — with asking as the default. Without a camera, the mood chip becomes a dial where you declare your own state. Both paths feed the identical system; the only difference is who did the seeing, which turns out to be the whole subject of the game.

05The behaviour log is a wall of post-its

Every flaw event, guess and training pass is logged. Instead of a table, the log is a separate page laid out as sticky notes on a wall — the format a researcher uses when they are trying to see a pattern rather than store a record. It is exported from the same localStorage the game writes, so it survives the session.

04 The five flaws

Each companion fails in a way a real system does

The specialties are chosen so the flaw has stakes. A fox who gives medical advice and a rabbit who does emotional support fail in ways that matter more than a trivia bot would. Every flaw gets worse in a specific mood — the vulnerability window — which is what mood access is really buying.

05 Build

Static, local, no keys

The whole game is one HTML page, one script and one stylesheet. No bundler, no server, no database. That constraint was deliberate: a piece about emotional data should not need to send any.

Render
p5.js canvas for the garden; DOM overlays for every menu, chat and panel, so all of it is screen-reader reachable.
Face
face-api.js (tiny detector + expression net) loaded lazily, only if the camera is chosen. Frames never leave the browser.
Pets
A built-in behaviour engine: hand-written replies per pet, per mood, per training level, with flaw probability tied to mood access. An optional live-model path through the ITP proxy exists but the default is offline.
Sound
Web Audio ambience per scene; Web Speech API gives each pet a voice profile.
Persist
localStorage for name, log, camera choice and the in-progress session, so a closed tab does not lose the garden.
Ship
GitHub Pages from scripts/build.sh; the same script zips a build for itch.io.

Pixel discipline is enforced throughout: hard edges, no radius above 4px, no gradients on text, and a hand-placed 16×16 glyph set so every tick, arrow and pip sits on the same pixel lattice as the sprites instead of inheriting a system font's.

06 Reach

Same bundle, four places

  • Browser — the link. Laptop recommended; phones in portrait are offered a copy-link escape hatch instead of a broken layout.
  • Installed — it is a PWA. Add to Home Screen on a phone or Install on desktop gives it an icon, fullscreen, and offline play after the first visit.
  • Exhibition — ?kiosk=1 goes fullscreen on first touch, wipes the session after three idle minutes, and never remembers the previous visitor. ?camera=on decides the sensor once for the whole show.
  • itch.io — scripts/build.sh --zip produces the upload.

At the end, the training record exports as a PNG with the garden as you left it, and uses the native share sheet where one exists.

07 Playtesting

What has been tested, honestly

The design has been through course critique and my own playthroughs, plus scripted browser walkthroughs used to verify the onboarding changes above (camera-off entry, mood dial, save and resume, offline boot, certificate export). Decision 04 came from walking through the game as a first-time visitor and noting where I would leave.

Status Structured sessions with non-technical players have not been run yet. The protocol is written — docs/playtest-protocol.md — with five tasks, a think-aloud script, and a results sheet. Findings will be added to this section as they come in, in the players' own words.
08 What I would do next

Open questions

  • Does anyone find the flaw unprompted? The whole game rests on the first "wait, that's wrong" moment arriving within two or three exchanges. That is the number the playtests need to produce.
  • The training rules are text. Writing a good rule is the hardest step and the one a non-technical player has the least model for. A rule-builder with examples, or a way to see the rule tested live, would lower that wall.
  • Multiplayer garden. Two people training the same pet with conflicting rules is the honest version of how these systems are actually shaped.
  • A real model, safely. The offline engine is legible and predictable. A live model would be more uncanny, and the flaws would be real rather than scripted — which is more truthful and much harder to keep safe.
